프로젝트 개요

한기대 공지비서는 학교·학과 게시판과 온통청년의 청년정책을 모아, 사용자에게 필요한 정보를 제공하는 자동 브리핑 서비스입니다. 학교 공지는 AI가 대상, 마감일, 할 일, 준비물 등을 정리하고, 사용자 설정과 비교해 관련도 별점과 판단 이유를 표시합니다. 결과는 웹페이지에서 확인할 수 있으며, 매일 오전 11시에는 디스코드 브리핑으로 받아볼 수 있습니다.

  • GitHub Actions가 하루 4회 공지 수집과 분석을 실행합니다.
  • 별도 서버 없이 GitHub Actions와 GitHub Pages, 무료 API를 활용해 운영하도록 구성했습니다.

주요 기능

  • 학교 일반·장학·학사 게시판과 사용자가 설정한 학과 게시판에서 공지를 수집합니다.
  • AI가 공지의 본문과 이미지에서 대상, 마감일, 할 일, 준비물, 분류 등을 정리합니다.
  • 사용자 설정과 공지 내용을 비교해 0~3점의 관련도와 판단 이유를 표시합니다.
  • 온통청년 정책은 API의 나이·지역·신청 기간 정보를 바탕으로 수집하고 관련도를 계산합니다. 정책 정보에는 이미 조건이 항목별로 정리되어 있어 AI를 거치지 않습니다.
  • 기상청 날씨, 새 공지, 마감 임박 공지를 디스코드와 웹페이지에서 확인할 수 있습니다.
  • 웹페이지에서 공지를 분류별로 확인하고 관련도순·마감순으로 정렬할 수 있습니다.

구현 내용

학교·학과 게시판 크롤러와 온통청년 정책 수집 모듈이 데이터를 모으고, 공통 JSON 형식으로 저장합니다. 학교 공지는 AI 정보 추출과 관련도 계산을 거쳐 디스코드와 웹페이지에 표시됩니다. 온통청년 정책은 API에서 받은 조건을 기준으로 관련도를 계산합니다.

전체 과정은 다음 순서로 실행됩니다.
학교·학과 공지 및 청년정책 수집 → 공지 정보 정리 → 사용자 설정과 관련도 계산 → 디스코드·웹페이지에 표시

실행 방법

1.이 저장소 오른쪽 위 Use this template → Create a new repository로 내 저장소를 만듭니다. (Public 권장)
2. 내 저장소 Settings → Secrets and variables → Actions → New repository secret에서 위의 키 4개를 같은 이름으로 등록합니다. (청년정책을 안 쓰면 YOUTH_API_KEY는 빼도 됩니다)
3. Settings → Actions → General → Workflow permissions에서 Read and write permissions를 고르고 저장합니다.
4. Settings → Pages에서 Source를 Deploy from a branch, Branch를 main / docs로 고르고 저장합니다.
5. Issues → New issue → 내 설정 바꾸기에서 내 학과, 학년, 관심 분야를 고르고 제출합니다. 청년정책을 받으려면 출생연도와 **거주 지역(주민등록상 주소)**도 넣습니다. 1분쯤 뒤 설정이 적용되고 이슈가 닫힙니다.
6. Actions → 공지 자동 정리 → Run workflow로 첫 실행을 합니다. 이후로는 하루 4번 자동으로 실행됩니다.
7. https://내아이디.github.io/저장소이름/에서 웹페이지를 확인합니다. 웹페이지와 디스코드 링크는 내 저장소 주소를 자동으로 따라갑니다.

내 역할

공지·청년정책 수집 · 4인 팀

학교·학과 게시판 크롤러와 온통청년 청년정책 수집 기능을 맡았습니다. 학교 게시판에서 제목, 게시일, 링크, 본문과 이미지 주소를 수집하고, 사용자 설정에 맞는 학과 게시판을 선택하도록 구현했습니다.
온통청년 API에서 지역과 신청 기간에 맞는 정책을 가져와 프로젝트의 공통 JSON 형식으로 변환했습니다. 이를 통해 수집된 청년정책도 다른 공지 데이터와 함께 후속 처리 과정에서 활용할 수 있도록 했습니다.

  • #6 일반·장학·학사 공지 크롤러
  • #9 공지 누적 저장 및 신규 공지 표시
  • #34 학과별 공지 수집 추가
  • #52 온통청년 정책 수집 추가

저장된 공지 중 본문이 있는 항목은 상세 페이지를 다시 요청하지 않도록 처리했습니다. 새 공지는 ID를 기준으로 기존 데이터에 추가하고, 기존 공지라도 본문이 비어 있으면 다시 수집한 본문과 이미지 정보로 보완합니다.

느낀 점 및 향후 개선점

처음에는 게시판에서 정보를 가져오는 것이 크롤러의 핵심이라고 생각했지만, 중복을 구분하고 누락된 본문을 보완하는 과정도 중요하다는 점을 배웠습니다. 실제 웹사이트에서는 응답 지연이나 본문 누락 같은 예외가 생길 수 있어, 한 번 실행되는 것뿐 아니라 기존 데이터가 잘 유지되는지도 확인해야 했습니다. 또한 수집 데이터가 AI 정리, 관련도 계산, 웹페이지와 디스코드로 이어지는 것을 보며 팀원 간 데이터 형식과 진행 상황을 공유하는 일이 중요하다는 점을 경험했습니다.

생활관과 반도체·디스플레이공학과 게시판은 사이트 구조가 달라 별도의 수집 방식이 필요해 후속 과제로 남았습니다.
각 게시판에 맞는 수집 로직과 테스트를 추가하고, GitHub Actions의 예약 실행 지연과 설정 양식의 불편함도 개선할 수 있습니다.
